# PAR-012: Spend Execution Flag Derivation

> **Authoritative requirement:** [PAR-012](../NORMATIVE.md#PAR-012)
> **Verification:** [VERIFICATION.md](../VERIFICATION.md)
> **Tracking:** [TRACKING.yaml](../TRACKING.yaml)

---

## Summary

Chia L1 does not execute a spend bundle under the flags a caller supplies. It executes it under those flags combined with two further sets: the hard-fork flags activated at the bundle's height, and `MEMPOOL_MODE`. `dig-clvm` must reach the same combined value, because the flags select the CLVM dialect, the condition parser's strictness, and the cost schedule — three inputs that decide whether a spend is valid.

Through `chia-consensus` 0.26 this derivation was invisible to callers. `run_spendbundle()` took a `height` argument and computed the combination itself:

```rust
let flags = get_flags_for_height_and_constants(height, constants) | flags | MEMPOOL_MODE;
```

`chia-consensus` 0.36 removed the `height` parameter and the derivation with it. `run_spendbundle()` now applies the `flags` argument verbatim. The derivation therefore moved to the caller, and `dig-clvm` owns it.

## Specification

`ValidationContext` MUST expose the derivation, and every `run_spendbundle()` call site MUST use it:

```rust
impl ValidationContext {
    pub fn spend_flags(&self, extra: u32) -> u32 {
        get_flags_for_height_and_constants(self.height, self.constants.consensus())
            | extra
            | MEMPOOL_MODE
    }
}
```

`extra` carries the caller's flags. For `validate_spend_bundle()` those are `ValidationConfig::flags`; for `build_block_generator()` they are `DONT_VALIDATE_SIGNATURE`; for the `validate_clvm_and_signature()` path they are `0`, because 0.26's `validate_clvm_and_signature()` hard-coded `0` for the caller flags and passing anything else would change validation behaviour rather than preserve it.

`validate_block()` is out of scope: it calls `run_block_generator2()`, which never derived flags in any version and still forwards `ValidationConfig::flags` unchanged.

Both DIG networks set `hard_fork2_height = 0`, so `get_flags_for_height_and_constants()` returns `ENABLE_KECCAK_OPS_OUTSIDE_GUARD | COST_CONDITIONS | SIMPLE_GENERATOR` at every height. These are not conditional flags on DIG — they are always active, and dropping them changes the cost schedule for every spend.

## Acceptance Criteria

- [x] `ValidationContext::spend_flags()` returns `get_flags_for_height_and_constants(height, constants) | extra | MEMPOOL_MODE`.
- [x] All three `run_spendbundle()` call sites and the `validate_clvm_and_signature()` call site use it.
- [x] A test asserts the composition against flag constants stated independently of the helper, not read back out of it.
- [x] A test proves `NO_UNKNOWN_CONDS` — a `MEMPOOL_MODE` component — reaches the condition parser, by driving a spend whose acceptance depends on it.

## Implementation Notes

- **Primary files:** `src/consensus/context.rs` (the derivation), `src/consensus/validate.rs` and `src/consensus/block.rs` (the call sites).
- **The failure mode is silent.** Deleting the `height` argument and keeping `config.flags` compiles, runs, and returns plausible results. It is a consensus divergence with no error at any layer, which is why PAR-012 requires a behavioural assertion and not only a structural one.
- **Assertions must not be circular.** A test that computes its expected value with `get_flags_for_height_and_constants()` passes for any implementation that also calls it, including one that drops `MEMPOOL_MODE`. `tests/vv_req_par_012.rs` composes the expected value from named flag constants instead.
